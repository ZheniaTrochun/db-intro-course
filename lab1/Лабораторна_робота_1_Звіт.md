# Лабораторна робота 1: Збір вимог та розробка схеми ER

**Тема проєкту:** Система управління гуртожитком та супутніми сервісами для студентів (розподіл по кімнатах, парковка, пошук роботи, обліковий запис користувача)

---

## 1. Короткий виклад вимог

### Зацікавлені сторони
- **Студент** — основний користувач системи, який реєструється, отримує кімнату в гуртожитку, за бажанням займає парковочне місце та відстежує пропозиції роботи.
- **Адміністратор гуртожитку** — відповідає за гуртожиток.

### Призначення системи
Система повинна автоматизувати процес заселення студентів у гуртожиток, облік вільних/зайнятих кімнат та парковочних місць, а також вести облік пропозицій роботи (вакансій), доступних студентам. В основі системи лежить єдиний обліковий запис користувача ("User"), на базі якого створюється профіль студента або адміністратора.

### Ключові дані, які потрібно зберігати
- Облікові дані користувача (ім'я, email, дата народження, дата реєстрації, статус)
- Дані студента (рік вступу, факультет, курс навчання, статус навчання)
- Дані гуртожитку, кімнат і парковочних місць та їх зайнятість
- Дані про вакансії, на які може відгукнутись студент.

### Основні операції, які має підтримувати система
- Реєстрація нового користувача та створення профілю студента
- Зарахування студента на курс навчання
- Призначення студенту кімнати в гуртожитку
- Призначення/звільнення парковочного місця
- Подача студентом заявки на вакансію
- Призначення адміністратора на конкретний гуртожиток

---

## 2. ER-діаграма

*(Діаграма додається окремим зображенням — див. файл схеми. Нижче наведено її текстовий опис для звіту.)*

Схема містить 11 сутностей: "User", "Student", "Dorm admin", "Department", "Course", "Enrollment", "Dorm", "Rooms", "Parking slot", "Vacancy", "Application".

"Enrollment" та "Application" — асоціативні сутності (junction-таблиці), які реалізують зв'язки "багато-до-багатьох": студент може записатись на кілька курсів, а курс може мати кількох студентів (через "Enrollment"); студент може подати заявки на кілька вакансій, а вакансія може отримати заявки від кількох студентів (через "Application").

## 3. Список сутностей та атрибутів

### User (Користувач)
| Атрибут | Опис |
|---|---|
| **UserID** (PK) | Унікальний ідентифікатор облікового запису |
| First name | Ім'я |
| Last name | Прізвище |
| Email | Використовується для входу в систему (UNIQUE) |
| Date of birth | Дата народження |
| Registration date | Дата створення облікового запису |
| Status | Стан облікового запису (наприклад, active / blocked) |

### Student (Студент)
| Атрибут | Опис |
|---|---|
| **StudentID** (PK) | Унікальний ідентифікатор студента |
| EnrollmentYear | Рік вступу |
| DormID (FK) | Гуртожиток, до якого прикріплений студент (може бути `NULL`, якщо ще не призначено) |
| RoomID (FK) | Кімната, у якій мешкає студент (може бути `NULL`, доки не призначено кімнату) |
| Status | Статус навчання (`enum student_status`: enrolled / on_leave / graduated / expelled) |
| UserID (FK) | Пов'язаний обліковий запис. Особисті дані (ім'я, прізвище, email) не дублюються — беруться з "User" через join |

### Dorm admin (Адміністратор гуртожитку)
| Атрибут | Опис |
|---|---|
| **AdminID** (PK) | Унікальний ідентифікатор адміністратора |
| UserID (FK) | Пов'язаний обліковий запис. Особисті дані беруться з "User" через join, без дублювання |
| DormID (FK) | Гуртожиток, за який відповідає адміністратор |

### Department (Факультет/Кафедра)
| Атрибут | Опис |
|---|---|
| **DepartmentID** (PK) | Унікальний ідентифікатор підрозділу |
| DepartmentName | Назва факультету/кафедри |

### Course (Курс навчання)
| Атрибут | Опис |
|---|---|
| **CourseID** (PK) | Унікальний ідентифікатор курсу |
| DepartmentID (FK) | Факультет, до якого належить курс |
| CourseTitle | Назва курсу |

### Enrollment (Запис про зарахування на курс)
Асоціативна сутність, що реалізує зв'язок "багато-до-багатьох" між "Student" та "Course": один студент може бути записаний на кілька курсів, а на один курс можуть бути записані кілька студентів.

| Атрибут | Опис |
|---|---|
| **EnrollmentID** (PK) | Унікальний ідентифікатор запису про зарахування |
| StudentID (FK) | Студент, який записаний на курс |
| CourseID (FK) | Курс, на який записаний студент |
| EnrollmentDate | Дата зарахування на курс |
| Grade | Оцінка/результат (`NULL`, доки курс не завершено) |

### Dorm (Гуртожиток)
| Атрибут | Опис |
|---|---|
| **DormID** (PK) | Унікальний ідентифікатор гуртожитку |
| Address (UK) | Адреса гуртожитку (унікальна) |

### Rooms (Кімнати)
| Атрибут | Опис |
|---|---|
| **RoomID** (PK) | Унікальний ідентифікатор кімнати |
| DormID (FK) | Гуртожиток, якому належить кімната |
| RoomNumber | Номер кімнати |
| Floor | Поверх, на якому розташована кімната |

Зв'язок із студентами реалізований в інший бік: FK на кімнату (`RoomID`) знаходиться в сутності "Student", оскільки одна кімната може мешкати кількох студентів, а студент прикріплений щонайбільше до однієї кімнати (детальніше — розділ 4).

### Parking slot (Парковочне місце)
| Атрибут | Опис |
|---|---|
| **ParkingSlotID** (PK) | Унікальний ідентифікатор парковочного місця |
| StudentID (FK) | Студент, який займає місце (може бути `NULL` — вільне місце) |
| DormID (FK) | Гуртожиток, до якого прикріплене місце |
| AdminID (FK) | Адміністратор, який призначив місце (може бути `NULL`, якщо ще не оброблено) |
| SlotNumber | Номер парковочного місця |

### Vacancy (Вакансія)
Каталог вакансій компаній-партнерів університету. Доступна багатьом студентам одночасно; зв'язок із заявками студентів реалізується через асоціативну сутність "Application".

| Атрибут | Опис |
|---|---|
| **VacancyID** (PK) | Унікальний ідентифікатор вакансії |
| CompanyName | Назва компанії-партнера |
| JobName | Назва посади |

### Application (Заявка на вакансію)
Асоціативна сутність, що реалізує зв'язок "багато-до-багатьох" між "Student" та "Vacancy": студент може подати заявки на кілька вакансій, а одна вакансія може отримати заявки від кількох студентів.

| Атрибут | Опис |
|---|---|
| **ApplicationID** (PK) | Унікальний ідентифікатор заявки |
| StudentID (FK) | Студент, який подав заявку |
| VacancyID (FK) | Вакансія, на яку подано заявку |
| ApplicationDate | Дата подачі заявки |
| Status | Стан заявки (наприклад, `submitted` / `accepted` / `rejected`) |

## 4. Пояснення зв'язків

- **Department 1 — N Course.** Один факультет може мати багато курсів навчання; кожен курс належить рівно одному факультету.
- **Course 1 — N Enrollment** та **Student 1 — N Enrollment.** Реалізує зв'язок "багато-до-багатьох" між "Student" і "Course" через асоціативну сутність "Enrollment": студент може записатись на кілька курсів, курс може мати кількох студентів; кожен запис "Enrollment" прив'язаний рівно до одного студента і одного курсу.
- **Vacancy 1 — N Application** та **Student 1 — N Application.** Реалізує зв'язок "багато-до-багатьох" між "Student" і "Vacancy" через асоціативну сутність "Application": вакансія доступна багатьом студентам, студент може подати заявки на кілька вакансій; кожна заявка прив'язана рівно до одного студента і однієї вакансії.
- **User 1 — 0..1 Student** та **User 1 — 0..1 Dorm admin.** Один обліковий запис може мати не більше одного пов'язаного профілю — або студента, або адміністратора, але не обидва одночасно (User виступає надтипом/supertype для ролей у системі).
- **Dorm 1 — N Student.** Один гуртожиток вміщує багатьох студентів; студент може бути ще не прикріплений до жодного гуртожитку (`DormID` може бути `NULL`).
- **Dorm 1 — N Rooms.** Один гуртожиток містить багато кімнат; кожна кімната належить рівно одному гуртожитку.
- **Rooms 0..N — Student 0..1.** Одна кімната може вміщувати від 0 до кількох студентів (ліміт, наприклад, 4 особи, перевіряється тригером); кожен студент прикріплений щонайбільше до однієї кімнати (`RoomID` може бути `NULL`, доки кімнату не призначено). FK `RoomID` зберігається в сутності "Student" (на стороні "багато"), а не в "Rooms".
- **Dorm 1 — N Parking slot.** Гуртожиток має багато парковочних місць; кожне місце належить одному гуртожитку.
- **Student 0..1 — Parking slot 0..1.** Студент може займати не більше одного парковочного місця одночасно; місце може бути вільним (`StudentID = NULL`).
- **Dorm admin 0..1 — N Parking slot.** Паркомісце може мати призначеного адміністратора, але це не обов'язково (`AdminID` може бути `NULL`).
- **Dorm 1 — N Dorm admin.** Кожен гуртожиток повинен мати щонайменше одного адміністратора; кожен адміністратор відповідає рівно за один гуртожиток.

## 5. Бізнес-логіка та обмеження

### 5.1. Обмеження сутностей та атрибутів
- **Унікальність облікових записів:** поле "Email" у сутності "User" має бути глобально унікальним ("UNIQUE"), оскільки використовується для автентифікації.
- **Унікальність адреси гуртожитку:** поле "Address" у сутності "Dorm" має бути унікальним ("UNIQUE"), щоб уникнути дублювання записів про один і той самий гуртожиток.
- **Єдиність ролі користувача:** кожен запис "User" може мати рівно один пов'язаний профіль ("Student" або "Dorm admin"), але не обидва одночасно.
- **Статус студента:** атрибут "Status" у сутності "Student" набуває значень з обмеженого переліку (наприклад, "'active'", "'graduated'", "'expelled'").
- **Обов'язковість дати реєстрації:** "Registration date" заповнюється автоматично ("DEFAULT CURRENT_DATE") при створенні запису "User".
- **Нормалізація рольових сутностей:** "Student" і "Dorm admin" не зберігають особисті дані (ім'я, прізвище, email) повторно — ці дані доступні лише через join з "User" за полем "UserID" (FK). Це усуває дублювання та ризик розбіжності даних між "User" і рольовими таблицями.

### 5.2. Бізнес-правила процесів
- **Місткість кімнати:** кількість студентів, прикріплених до однієї кімнати ("RoomID" у "Student"), не повинна перевищувати встановлений ліміт (наприклад, 4 особи) — перевіряється тригером "BEFORE INSERT/UPDATE", оскільки стандартний "CHECK" не може рахувати кількість пов'язаних рядків.
- **Одне парковочне місце на студента:** студент може займати не більше одного "Parking slot" одночасно — "UNIQUE(StudentID)" у сутності "Parking slot".
- **Призначення адміністратора:** кожен "Dorm" повинен мати хоча б одного призначеного "Dorm admin".
- **Унікальність зарахування на курс:** пара "(StudentID, CourseID)" у сутності "Enrollment" має бути унікальною — "UNIQUE(StudentID, CourseID)", щоб студент не міг двічі записатись на той самий курс.
- **Унікальність заявки на вакансію:** пара "(StudentID, VacancyID)" у сутності "Application" має бути унікальною — "UNIQUE(StudentID, VacancyID)", щоб уникнути дублікатів заявок на ту саму вакансію. Студент може мати кілька записів "Application" одночасно (заявки на різні вакансії).

### 5.3. Посилальна цілісність
- **Rooms → Dorm:** кожна кімната обов'язково прив'язана до існуючого гуртожитку ("FK DormID NOT NULL").
- **Dorm admin → Dorm:** адміністратор без прив'язки до конкретного гуртожитку не має сенсу в моделі — "FK DormID NOT NULL".
- **Student → Room:** "FK RoomID" може бути "NULL" (студента ще не розподілено по кімнатах); якщо задано — повинно посилатись на існуючий запис "Rooms".
- **Parking slot → Student:** значення "StudentID" у "Parking slot" може існувати лише за умови наявності відповідного запису в "Student" (referential integrity), або бути "NULL", якщо місце вільне.
- **Parking slot → Dorm admin:** значення "AdminID" аналогічно може бути "NULL", якщо місце ще не опрацьоване жодним адміністратором.
- **Enrollment / Application → Student, Course / Vacancy:** усі FK в асоціативних сутностях є "NOT NULL" — запис про зарахування чи заявку не має сенсу без обох пов'язаних сторін.
- **Каскадність видалення:** при видаленні запису "Student" пов'язані записи в "Parking slot" (поле "StudentID") повинні оброблятися за правилом "ON DELETE SET NULL" (місце звільняється, а не видаляється), тоді як записи в "Enrollment" та "Application" — за правилом "ON DELETE CASCADE" (вони не мають сенсу без студента).

## 6. Припущення та обмеження моделі

1. **Компанія зберігається як текстове поле.** Атрибут "CompanyName" у сутності "Vacancy" зберігається як просте текстове поле, без виокремлення в окрему сутність "Company" — припускається, що додаткові атрибути компанії (адреса, контакти тощо) не потрібні для цієї моделі.
2. **Обмеження, що не виражаються нотацією ER.** Максимальна кількість студентів у кімнаті (наприклад, 4) та умови унікальності пар у "Enrollment" й "Application" не можуть бути показані засобами crow's foot нотації й реалізуються на рівні тригерів/"UNIQUE"-обмежень у фізичній схемі (див. розділ 5).
