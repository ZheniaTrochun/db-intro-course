#### 2. Основні рішення та огляд

1. **Додавання даних (`INSERT INTO`):**
   - Перевірено коректність підстановки значень за замовчуванням (`DEFAULT`), зокрема для статусів, пріоритетів та кольорів категорій.
   - Забезпечено валідацію роботи зі специфічними типами даних PostgreSQL:
     - Одновимірні масиви днів тижня типізовано як `SMALLINT[]` (`ARRAY[1, 3, 5]::SMALLINT[]`)
     - Часові мітки та дати обробляються через `CURRENT_DATE`, `CURRENT_TIMESTAMP`, а також комбінацію дати й часу `CURRENT_DATE + TIME '07:30:00'`
   - Протестовано збереження зв'язності моделі під час створення записів зі значеннями зовнішніх ключів (`FK`)

2. **Точкове оновлення (`UPDATE`):**
   - Для запобігання ненавмисному масовому оновленню даних усі інструкції суворо обмежені умовою `WHERE` (наприклад, за первинним ключем або складеною умовою `WHERE user_id = 2 AND workspace_id = 1`)
   - Активно застосовано конструкцію `RETURNING *`, що повертає модифіковані рядки у клієнтський результат і виключає необхідність виконання повторних запитів `SELECT`
   - Оновлення специфічних атрибутів: зміна часового поясу (`timezone = 'Europe/Kyiv'`), статусу звички (`'ACTIVE'` / `'PAUSED'`), прав доступу (`role = 'OWNER'`), а також кольорів і дедлайнів

3. **Безпечне видалення (`DELETE`):**
   - Реалізовано контрольоване видалення даних із застосуванням фільтрів `WHERE`:
     - Очищення записів без імені (`WHERE name IS NULL`)
     - Видалення неактивних звичок (`WHERE status = 'PAUSED'`)
     - Вилучення учасника з робочого простору за складеною умовою (`WHERE user_id = 1 AND workspace_id = 3`)
   - Використано `RETURNING *` для логування та аудиту видалених записів

4. **Вибірка та перевірка даних (`SELECT`):**
   - Реалізовано вибірки для типових користувацьких сценаріїв: пошук за автором (`WHERE creator_id = 1`), вибірка за колірною міткою, фільтрація заповнених полів (`WHERE workspace_id IS NOT NULL`)
   - Використано проєкцію лише конкретних атрибутів замість надлишкового `SELECT *` у продуктивних сценаріях
   - Застосовано сортування `ORDER BY` та лімітування `LIMIT` (наприклад, для відсортованого перегляду останніх виконань або перших користувачів)

#### 3. SQL-запити та верифікація заповнення

Усі операції згруповано у скрипті [`./oltp.sql`](./oltp.sql) за чотирма класичними розділами DML:
- **`--- INSERT ---`**: додавання нових екземплярів сутностей у кожну таблицю
- **`--- UPDATE ---`**: модифікація полів і статусів із перевіркою коректності
- **`--- DELETE ---`**: безпечне видалення записів
- **`--- SELECT ---`**: отримання даних за критеріями для верифікації стану бази

Для контролю початкового стану схеми також може бути використаний скрипт наповнення з попередньої роботи:
> **Скрипт початкового наповнення даними:** [`../2 - DDL/Lab-2-inserts.sql`](../2%20-%20DDL/Lab-2-inserts.sql)

Після кожного розділу або ключової модифікації виконується контрольний запит `SELECT` або повернення результату через `RETURNING *` для підтвердження успішності операції

### Висновок

У ході виконання лабораторної роботи:
1. Практично закріплено навички написання типових OLTP-запитів маніпулювання даними (DML) у PostgreSQL
2. Реалізовано повний цикл операцій `INSERT`, `UPDATE`, `DELETE` та `SELECT` у єдиному структурованому скрипті [`./oltp.sql`](./oltp.sql)
3. Відпрацьовано безпечні підходи роботи з даними: обов'язкове використання фільтрації `WHERE`, застосування `RETURNING *` для аудиту операцій, а також робота з масивами (`SMALLINT[]`) та часовими мітками (`TIMESTAMPTZ`)
4. Підтверджено коректну поведінку схеми Trackly та дієвість накладених раніше обмежень цілісності (`CHECK`, `NOT NULL`, `DEFAULT`, `FK`)
