# 1. Архітектурне рішення: Концептуальна модель даних та первинні ключі для Logistics

## Статус
Прийнято (оновлено: таблиці сполучення переведено на складений первинний ключ). Доповнено ADR 0002: тригери прибрано, логіку залишків і статусів не реалізовано в БД.

## Контекст
Необхідно розробити концептуальну схему бази даних (ERD) для системи управління складом та логістикою `logistics`. Схема повинна підтримувати відстеження постачань, локацій, оперативного стану залишків та внутрішніх переміщень, а також відповідати навчальним стандартам курсу PostgreSQL.

## Рішення
1. **Сутності з власним ідентифікатором використовують `INT GENERATED ALWAYS AS IDENTITY`:**
   - `supplier`, `product`, `warehouse_location`, `supply_order`, `inventory_movement`.
   - Відповідність стандарту SQL:2003 та матеріалам лекцій.
   - Забезпечує послідовну автоінкрементну генерацію первинних ключів.
2. **Таблиці сполучення мають складений первинний ключ з двох зовнішніх ключів:**
   - `inventory_stock`: `PRIMARY KEY (product_id, location_id)`. Один товар має один запис залишку в кожній комірці.
   - `supply_item`: `PRIMARY KEY (order_id, product_id)`. Один товар з'являється в накладній один раз, кількість і ціна фіксуються в цьому рядку.
   - Так вимагає лабораторна робота для зв'язків "багато-до-багатьох".
3. **Виділення `inventory_stock` як окремої сутності залишків:**
   - Зберігає оперативний стан "що, де і скільки лежить зараз" у конкретній комірці для миттєвих вибірок без важких агрегацій всієї історії дій.
4. **Виділення `supply_item` як окремої сутності:**
   - Розв'язує зв'язок "багато-до-багатьох" між товарами та накладними, фіксуючи кількість та закупівельну ціну на момент приходу.

## Наслідки
- Позитивні: Висока узгодженість даних, збереження історії цін, швидкий доступ до залишків, відсутність надлишкової складності з додатковими розширеннями ключів. Складений PK гарантує відсутність дублікатів пари товар-комірка і товар-накладна на рівні БД.
- Негативні: Залежність від послідовної генерації ідентифікаторів у межах однієї бази даних. Для накладної не можна внести один товар двома рядками (наприклад, з різними цінами); якщо це знадобиться, PK потрібно буде переглянути.
