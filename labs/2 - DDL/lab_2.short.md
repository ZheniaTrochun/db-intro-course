# ТЗ: Лабораторна робота 2 — ER-діаграма → схема PostgreSQL

## Мета
Перетворити ERD з лаб. 1 на реляційну схему: написати DDL, наповнити таблиці тестовими даними, перевірити в pgAdmin.

## Що зробити

1. **Підготовка**
   - перевірити, що на ERD є всі сутності та зв'язки (за потреби переглянути ERD: розділити/об'єднати таблиці, додати зв'язки);
   - визначити PK для кожної сутності;
   - *(за бажанням)* намалювати діаграму схеми (draw.io, DbDiagram, на папері).

2. **Правила перетворення ERD → таблиці**
   - сутність → таблиця;
   - зв'язок 1:N → зовнішній ключ на стороні «багато»;
   - зв'язок M:N → таблиця-зв'язка зі **складеним PK**.

3. **CREATE TABLE** для кожної таблиці
   - назва та стовпці з відповідними типами даних:
     - `INTEGER` / `SERIAL` (id, кількість), `VARCHAR(n)` (короткий текст), `TEXT` (довгий текст), `DATE` / `TIMESTAMP` (дати), `NUMERIC` (точні числа);
   - `NOT NULL` для обов'язкових полів;
   - `DEFAULT`, де це доречно (необов'язково);
   - `UNIQUE` там, де значення мають бути унікальними.

4. **Ключі та обмеження**
   - `PRIMARY KEY` у кожній таблиці (один або кілька стовпців);
   - `FOREIGN KEY ... REFERENCES ...` для кожного зв'язку;
   - `CHECK` для простих правил (напр. `CHECK (price > 0)`);
   - за бажанням іменувати обмеження через `CONSTRAINT`.

   Приклад:
   ```sql
   CREATE TABLE products (
       product_id  SERIAL PRIMARY KEY,
       name        VARCHAR(100) NOT NULL,
       price       NUMERIC(8,2) NOT NULL CHECK (price > 0),
       category_id INTEGER REFERENCES categories(category_id)
   );
   ```

5. **INSERT зразкових даних**
   - у кожну таблицю мінімум **3–5 змістовних рядків**;
   - спочатку батьківські таблиці, потім дочірні (щоб FK працювали);
   - дані мають відповідати обмеженням (FK, `NOT NULL`, `CHECK`).

6. **Перевірка в pgAdmin**
   - виконати `CREATE TABLE`, потім `INSERT`;
   - виправити помилки синтаксису та обмежень;
   - перевірити дані через `SELECT * FROM table;`.

## Поради для налагодження

- Помилка `CREATE TABLE` → перевірити рядок з помилки (назва типу, відсутня кома).
- Помилка `INSERT` → перевірити FK та `NOT NULL`; дублікат ключа = той самий PK вставлено двічі.
- Порушення FK → спершу вставити батьківський рядок.

## Що здати

| № | Результат | Вимоги |
|---|-----------|--------|
| 1 | **SQL-скрипт** | усі `CREATE TABLE` та `INSERT` по порядку, з коментарями про таблиці |
| 2 | **Короткий звіт про схему** | кожна таблиця зі стовпцями та ключами; пояснення важливих обмежень і припущень (напр. «`Orders.customer_id` → `Customers(customer_id)`»); діаграма за потреби |
| 3 | **Доказ наповнення таблиць** | частина SQL-файлу або скріншоти (у кожній таблиці 3–5+ рядків) |
| 4 | **Скріншоти pgAdmin** (за бажанням) | таблиці, Query Tool, результати `SELECT *` |

## Критерії оцінювання

- **Коректність схеми**: усі таблиці є, стовпці й типи відповідають ER-моделі.
- **Синтаксис SQL**: `CREATE TABLE` та `INSERT` виконуються без помилок.
- **Ключі**: у кожній таблиці є PK, FK правильно передають зв'язки.
- **Обмеження**: змістовне використання `NOT NULL`, `UNIQUE`, `CHECK`.
- **Узгодженість даних**: FK відповідають існуючим PK, немає зайвих `NULL`, виконуються `CHECK`.
- **Документація**: чітке й точне пояснення схеми.
