# Lab 5 — Нормалізація БД (1NF–3NF)

## Завдання

Використовуючи схему VideoHub з Lab 2, провести аналіз нормалізації та продемонструвати її на практиці.

### Аналіз поточної схеми

1. Опис структури всіх таблиць (колонки, типи, ключі)
2. Перевірка **1NF** — атомарність значень (немає списків у комірках)
3. Перевірка **2NF** — відсутність часткових залежностей від композитного ключа
4. Перевірка **3NF** — відсутність транзитивних залежностей

### Денормалізований приклад (порушення)

1. Створити таблицю `VideoDenormalized` з трьома діагнозами:
   `tags` списком через кому (порушення 1NF),
   `category_and_subcategory` = 'Tech/Databases' (порушення 1NF),
   `author_username`/`author_email` транзитивно через автора (порушення 3NF)
2. Діагностика запитами: LIKE-пошук по списку тегів, дублі довідника автора
3. Продемонструвати **аномалію оновлення**: зміна email автора потребує оновлення багатьох рядків

### Нормалізація (виправлення)

1. `CREATE TABLE` — довідник `Tag` (UNIQUE name) + junction `VideoTag` (композитний PK)
2. `ALTER TABLE` — хірургія на живій таблиці: ADD атомарних колонок → перенесення даних через `split_part` → DROP складених/транзитивних колонок → RENAME
3. Наповнення M:N через `CROSS JOIN` + `ON CONFLICT DO NOTHING` (ідемпотентність)
4. Верифікація: той самий інфо-контент дістається через JOIN (дані не втрачені — переупаковані)
5. Порівняння до/після

### Висновок

- Чому поточна схема VideoHub вже в 3NF
- Коли денормалізація виправдана (свідомий вибір, а не помилка)
- Мнемоніка нормальних форм: «кожен неключовий атрибут залежить від ключа, усього ключа і нічого, крім ключа»
